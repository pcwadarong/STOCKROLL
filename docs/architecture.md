# STOCKROLL 기술 설계

기준일 2026-10-11. 규칙은 [AGENTS.md](../AGENTS.md)에, 여기는 **왜 그렇게 정했는지**를 둔다.

## 1. 한 장 요약

```
 기기 (브라우저 / 설치된 PWA)                               외부
┌───────────────────────────────────────────────┐
│  보정 끝난 JPEG ──┐                            │
│                  ▼                            │
│  entities/photo   EXIF 읽기 (GPS 제외)         │
│                  ▼                            │
│  entities/frame   레이아웃 계산 → 캔버스 그리기 │
│                  ▼                            │
│  shared/lib       JPEG 인코딩 → 저장 / 공유     │──▶ 편집기 사진은 여기서 끝. 밖으로 안 나감
│                                               │
│  장비·필름·레시피·촬영 기록 (텍스트 + 링크) ────│──▶ Supabase (Auth + Postgres, RLS)
│                                               │
│  레시피 예시 사진 (사용자가 직접 고른 1장)       │
│    └ shared/lib  긴 변 ≤1200 축소 + 재인코딩 ──│──▶ Supabase Storage (비공개 버킷, 본인만)
│                  = 메타데이터·GPS 제거          │
└───────────────────────────────────────────────┘
        ▲ 정적 파일 + 서비스워커
        │
     Vercel
```

편집기에서 연 사진은 기기 안에서만 흐른다. 서버로 가는 것은 텍스트 기록과, **사용자가 레시피에 직접 붙인 예시 사진 1장**(줄이고 메타데이터를 지운 사본)뿐이다. 이 경계가 설계 전체의 기준이고, 예외는 이것 하나다(§5).

## 2. 스택과 결정 근거

| 영역          | 선택                                   | 왜                                                                                                     | 안 고른 것                                                                                                     |
| ------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 프레임워크    | Vite + React SPA                       | 핵심 로직(Canvas·EXIF·파일 저장)이 전부 브라우저 API다. 서버 렌더링이 할 일이 없다                     | Next.js — 화면 대부분이 `'use client'`가 되고 서비스워커 설정이 번거롭다. 공개 갤러리(SEO)가 필요해지면 재검토 |

| 설치형 앱     | PWA (`vite-plugin-pwa`)                | PC·폰 한 코드로 설치. 스토어 심사 없음                                                                 | 네이티브 래퍼 — 개인용에 과하다                                                                                |
| 백엔드        | Supabase (Auth + Postgres)             | PC↔폰에서 같은 장비·레시피 목록을 쓰려면 계정과 DB가 필요하다. RLS로 서버 코드 없이 본인 데이터만 접근 | Firebase — 관계형 데이터(롤→컷, 레시피→버전)와 맞지 않는다. Drive JSON 동기화 — 충돌 처리를 직접 만들어야 한다 |

| 품질 도구     | ESLint + Prettier + husky + commitizen | chaen과 같은 규칙·커밋 타입을 써서 프로젝트 간 전환 비용을 없앤다                                      |                                                                                                                |

> **TypeScript는 6.x에 고정했다.** 7.x는 typescript-eslint 8의 지원 범위(`<6.1`) 밖이라 타입 기반 린트가 깨진다. typescript-eslint가 7을 지원하면 올린다.

> **`eslint-plugin-jsx-a11y`는 ESLint 10을 peer로 선언하지 않았다**(동작은 확인). 설치 시 peer 경고가 나오는 건 이 때문이다.

## 3. 프레임 엔진

### 좌표계

모든 치수는 **1080 폭 캔버스 기준**으로 정의하고, 실제 캔버스 폭에 비례해 `unit`을 곱한다. 출력 크기가 바뀌어도 여백과 글자의 비율이 유지된다.

```
 3:4 프리셋 (1080 × 1440) 에 3:2 가로 사진을 넣었을 때

 ┌──────────────────────────────┐ ─┐
 │            여백               │  │ 342   ← 위아래 여백이 같다
 │  ┌────────────────────────┐  │ ─┘
 │  │                        │  │
 │  │      사진 984 × 656     │  │   contain. 자르지 않는다
 │  │                        │  │
 │  └────────────────────────┘  │ ─┐ 26 (CAPTION_GAP)
 │  Shot on FUJIFILM X-T50  ISO…│ ─┤ 74 (CAPTION_HEIGHT)
 │  XF16-80mmF4 R OIS WR   ETER…│ ─┘
 │            여백               │    342
 └──────────────────────────────┘
  ◀48▶                      ◀48▶    MARGIN
```

### 왜 사진+캡션을 한 덩어리로 가운데 두나

캡션을 캔버스 바닥에 고정하면 가로 사진에서 사진과 캡션 사이가 300px 넘게 벌어져 캡션이 사진의 설명으로 읽히지 않는다. 덩어리로 묶어 세로 중앙에 두면 어떤 비율에서도 캡션이 사진에 붙는다.

### 계산과 그리기의 분리

| 파일                                          | 하는 일                                                                             | 의존                          |
| --------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------- |
| `entities/frame/model/style.ts`               | 스타일 타입·선택지·검증(`parseStyle`), 글자색(`inkFor`), 와이드 컷 영역(`cropRect`) | 없음 (순수 함수, Node 테스트) |
| `entities/frame/model/caption.ts`             | 템플릿 + 촬영 정보 → 캡션 줄(`buildCaption`), 줄 높이                               | 없음                          |
| `entities/frame/model/spec.ts`                | 스타일 + 캡션 → 레이아웃이 필요한 치수(`frameSpec`)                                 | 없음                          |
| `entities/frame/model/layout.ts`              | 사진 크기 + 프리셋 + 치수 → 사각형 좌표                                             | 없음                          |
| `entities/frame/lib/draw-frame.ts`            | 좌표대로 캔버스에 그리기, 글자 맞춤, 필름 스트립, 로고                              | Canvas 2D                     |
| `entities/frame/lib/fonts.ts`                 | 폰트 목록과 로딩(`ensureFont`)                                                      | `document.fonts`              |
| `features/frame-photo/lib/resolve-caption.ts` | 선택·EXIF·등록 장비 → 촬영 정보 문자열(`FrameInfo`)                                 | 없음                          |
| `features/frame-photo/model/*`                | 상태·파일 열기·내보내기 조립                                                        | React                         |

흐름은 한 방향이다: `FrameInfo` → `buildCaption` → `frameSpec` → `computeLayout` → `drawFrame`. 미리보기와 내보내기가 같은 길을 지나므로 둘이 달라질 수 없다.

### 템플릿

| 템플릿    | 캡션 위치     | 줄 구성                                               |
| --------- | ------------- | ----------------------------------------------------- |
| `label`   | 사진 아래     | 좌: 카메라·렌즈 / 우: 노출·룩 (처음부터 있던 모양)    |
| `center`  | 사진 아래     | 카메라 · 렌즈 / 노출 · 룩, 정렬 선택                  |
| `bar`     | 사진 아래     | 조리개·셔터·ISO·초점거리를 같은 폭의 칸으로           |
| `overlay` | 사진 위(하단) | `center`와 같은 줄, 밝은 글자 + 옅은 그림자           |
| `stamp`   | 사진 위(하단) | 호박색 세그먼트 글자. 좌: 날짜·카메라·렌즈 / 우: 노출 |
| `film`    | 필름 띠       | 사진 위아래 검은 띠와 퍼포레이션, 아래 띠에 룩과 노출 |
| `none`    | 사진 아래     | 촬영 정보 없음. 내 텍스트와 로고만                    |

| 결정                                                   | 왜                                                                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 템플릿과 옵션(배경·여백·위치·컷·폰트·크기·정렬)을 분리 | 템플릿마다 옵션을 따로 두면 조합이 폭발한다. 템플릿은 "무엇을 어디에", 옵션은 "어떻게 보이게"만 정한다 |
| 캡션 높이를 줄 수에서 계산해 레이아웃에 넘김           | 줄이 빠지면(필름 스캔) 캡션이 짧아지고 사진이 그만큼 커진다. 고정 높이면 빈 띠가 남는다                |
| 글자색은 배경색의 밝기로 계산                          | 컬러 피커로 어떤 색을 골라도 읽혀야 한다                                                               |
| 와이드 컷은 원본 좌표의 `source` 사각형으로            | 자르기가 레이아웃의 다른 계산에 섞이지 않는다. 컷이 없으면 사진 전체다                                 |
| 여백 0이어도 캡션은 좌우 24를 유지                     | 사진은 가장자리까지 가도 글자가 캔버스 끝에 붙으면 잘려 보인다                                         |
| 폰트는 고를 때만 불러오고 PWA가 미리 캐시              | 기본 모양에는 추가 다운로드가 없다. 오프라인에서도 같은 서체로 내보낸다                                |
| 로고는 캡션이 양쪽 정렬이면 가운데, 아니면 줄 위       | 양쪽 정렬은 가운데가 비어 있고, 가운데 정렬 줄과는 겹친다. 필름 띠에는 자리가 없어 그리지 않는다       |

### 캡션이 넘칠 때

좌우 문자열이 겹치면 ① 글자를 최대 62%까지 줄이고 ② 그래도 넘치면 **왼쪽만** 말줄임한다. 오른쪽(촬영값)은 숫자라 잘리면 틀린 정보가 된다.

| GPS                         | 읽지 않음                                           | 출력 JPEG는 캔버스 재인코딩이라 원본 EXIF가 없다. 샘플 후지 원본·Lightroom 보정본 모두 GPS가 들어 있었다 |
| 스캐너 정보                 | 카메라로 쓰지 않음                                  | 현상소 스캔은 Make/Model이 `NORITSU KOKI EZ Controller`다. 카메라 칸을 비우고 직접 입력을 안내한다       |

### 실제 파일 3장으로 확인한 것 (2026-10-11)

| 파일                          | 일반 EXIF     | 후지 MakerNotes                                                | 결론                                           |
| ----------------------------- | ------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| 후지 원본 JPEG (X-T50, 1.4MB) | 있음          | **있음** (1296바이트. 컬러 크롬·그레인·톤·WB 시프트 태그 확인) | 시뮬레이션·레시피 수치를 자동으로 읽을 수 있다 |
| Lightroom 보정본 (25.8MB)     | 있음          | **없음** (Lightroom이 지운다)                                  | 보정본만으로는 시뮬레이션을 알 수 없다         |
| 필름 스캔 (Noritsu, 7.1MB)    | 스캐너 정보뿐 | 없음                                                           | 전부 수동 입력                                 |

> **보정본에서 시뮬레이션을 자동으로 읽을 방법은 없다.** 자동 인식을 넣으려면 "원본 JPEG에서 정보를 읽고 보정본을 표시 이미지로 쓰는" 2파일 흐름이 필요하다. 그 전까지는 수동 입력이다.

> **EXIF는 파일 전체를 읽어서 파싱한다.** Blob을 그대로 넘기면 exifr가 앞부분만 읽는데, Lightroom 보정본은 EXIF가 그 범위 밖에 있어 **에러 없이 빈 결과**가 나온다(`entities/photo/lib/read-exif.ts`).

후지 MakerNotes 파서는 아직 없다. `exifr`는 MakerNote를 원시 바이트로만 주므로 후지 IFD를 직접 읽어야 한다.

## 5. 데이터 모델 (Supabase)

스키마: [`supabase/migrations/`](../supabase/migrations/) — 시작은 `20261011000000_init.sql`. 파일이 있다고 실제 프로젝트에 적용됐다는 뜻은 아니다. `20261011030000_recipe_photo.sql`(예시 사진)은 **작성만 했고 적용하지 않았다.**

```
 cameras ─┐                         recipes ──< recipe_versions
 lenses ──┤                                          │
 films ───┼──< rolls ──< shots >─────────────────────┘
          └────────────< shots
```

| 결정                                                         | 왜                                                                                                                                                            |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 장비 상태는 `status` 한 필드 (`ownership`은 읽지 않고 보존)  | 대여·판매도 "지금 찍을 수 있나, 아니면 왜"의 답이라 수리 중·전시용과 같은 목록에 둔다. 두 필드였을 때는 "Rented 인데 In use" 같은 조합이 화면을 복잡하게 했다 |
| 장비를 지우지 않음 (`on delete set null`은 안전망일 뿐)      | 과거 사진이 참조한다                                                                                                                                          |
| `recipes`와 `recipe_versions` 분리, 버전은 추가만            | 수치를 모르는 후보는 이름만 등록. 수치를 바꿔도 과거 기록이 가리키는 값이 유지된다                                                                            |
| `shots.simulation` / `recipe_version_id` / `final_look` 분리 | 촬영 당시 설정, 붙인 라벨, 최종 보정 결과는 서로 다른 사실이다                                                                                                |
| `shots.field_sources`                                        | 값마다 EXIF에서 왔는지 수동인지 남긴다                                                                                                                        |
| `films.usage`는 화면에서 쓰지 않음 (컬럼은 보존)             | 써 본 필름과 후보를 한 목록에 함께 올린다. 단계를 고르는 칸이 실제로 쓰이지 않았다. 구분이 필요하면 Note에 적는다                                             |
| 모든 테이블 RLS `user_id = auth.uid()`                       | 클라이언트가 DB를 직접 호출하므로 정책이 유일한 방어선이다                                                                                                    |
| 촬영 기록에는 사진 컬럼 없이 `drive_url`·`instagram_url`만   | 링크 저장과 파일 읽기는 다른 기능이다. 비공개 Drive 링크를 저장해도 앱이 사진을 읽을 수는 없다                                                                |
| Storage는 레시피 예시 사진에만 (`recipes.photo_path`)        | 아래 "레시피 예시 사진" 참고                                                                                                                                  |

`src/shared/api/supabase.ts`는 환경변수가 없으면 `null`이다. 프레임 제작은 로그인 없이도 동작해야 하기 때문이다.

### 레시피 예시 사진 — "사진은 서버에 올리지 않는다"의 유일한 예외

레시피 이름과 수치만으로는 그게 어떤 룩이었는지 기억나지 않는다. 그래서 레시피마다 예시 사진을 **한 장** 붙일 수 있게 했다. 편집기에서 여는 사진은 여전히 어디로도 가지 않는다.

```
 사용자가 고른 파일 (원본, EXIF·GPS 있음)
        │  shared/lib/resize-image.ts
        ▼
 긴 변 ≤ 1200px, JPEG 0.85, 캔버스 재인코딩 ── 메타데이터가 전부 사라진다
        │  entities/recipe/api/recipe-photo.ts
        ▼
 Storage  recipe-photos / {user_id} / {recipe_id}.jpg   (비공개, 1MB·image/jpeg 제한)
        │
        ▼
 recipes.photo_path = '{user_id}/{recipe_id}.jpg'       보여줄 때는 1시간짜리 서명 URL
```

| 결정                                                          | 왜                                                                                                                                             |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 원본이 아니라 줄여서 재인코딩한 사본만 올린다                 | 원본에는 GPS와 촬영 정보가 들어 있다(§4에서 확인). 캔버스를 거치면 EXIF가 통째로 빠진다. 태그를 골라 지우는 방식은 빠뜨린 태그가 조용히 남는다 |
| 비공개 버킷 + 서명 URL                                        | 공개 버킷은 경로만 알면 누구나 본다. 경로가 `user_id/recipe_id`라 추측이 어렵긴 해도 링크가 새면 끝이다                                        |
| 경로의 첫 조각이 `user_id`, 정책은 그것만 `auth.uid()`와 비교 | 클라이언트가 Storage를 직접 호출하므로 정책이 유일한 방어선이다. 테이블 RLS와 같은 원칙                                                        |
| 경로를 레시피 id로 고정 (`upsert`)                            | "레시피당 1장"이 규칙이 아니라 구조가 된다. 다시 올리면 같은 자리를 덮어써서 지난 파일이 쌓이지 않는다                                         |
| 버킷에 1MB·`image/jpeg` 제한                                  | 앱의 축소 단계를 건너뛴 요청(원본 업로드)을 Storage가 거절한다. 클라이언트 코드만 믿지 않는다                                                  |
| `photo_path`에 URL이 아니라 경로를 저장                       | 비공개 버킷의 URL은 서명이 만료된다                                                                                                            |
| 레시피 삭제는 `deleteRecipe`로 (사진 → 행 순서)               | 행을 지워도 파일은 남는다. DB 트리거로는 파일을 지울 수 없어서 앱이 Storage API로 먼저 지운다                                                  |

> **업로드와 `photo_path` 기록은 한 트랜잭션이 아니다.** 처음 붙일 때 행 갱신이 실패하면 방금 올린 파일을 지우고 에러를 던진다. 교체할 때는 경로가 같아 행을 다시 쓰지 않는다. 사진을 뗄 때는 행을 먼저 비우고 파일을 지운다 — 중간에 실패해도 "깨진 이미지"가 아니라 "사진 없음"으로 보이게 하기 위해서다.

> **`photoPath`는 폼 저장에 섞지 않는다.** `recipeCollection.save`에 오래된 `photoPath: null`을 실어 보내면 사진이 떨어지고 파일만 남는다. 이 값은 `uploadRecipePhoto`·`removeRecipePhoto`만 쓴다.

## 6. PWA

- `registerType: 'autoUpdate'` — 새 배포를 자동 반영. 편집 중 상태가 서버에 없어 갱신 충돌이 없다.
- `sw.js`와 `manifest.webmanifest`는 Vercel에서 `no-cache`. 서비스워커가 캐시되면 업데이트가 영영 안 온다.
- 폰에서 저장은 공유 시트(Web Share API)가 있으면 `공유` 버튼을 함께 보여준다. iOS 설치형 PWA에서 `<a download>`가 사진 앱으로 바로 가지 않기 때문이다.
